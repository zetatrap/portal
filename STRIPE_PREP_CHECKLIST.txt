VERSION DEFINITIVA - GUIA EJECUTIVA DE IMPLEMENTACION
=======================================================

ESTA ES LA VERSION DEFINITIVA Y EXACTA DEL PROYECTO.
No es una guía opcional. Es la base de trabajo que define la arquitectura, el flujo de venta, el manejo de licencias, los emails automáticos y la preparación para Stripe.

Objetivo principal:
Construir una tienda de beats robusta, segura y operativa, donde la compra sea el flujo central, el admin pueda subir y controlar el catálogo, y cada venta genere automáticamente un correo con licencia y ticket para el cliente y una copia para el negocio.

Reglas no negociables:
- La venta no se basa en login como centro del negocio.
- El beat se vende siempre junto a una licencia válida.
- El precio final debe calcularse en backend.
- La compra debe generar ticket + licencia PDF.
- El cliente debe recibir el email con documentos.
- El negocio debe recibir el duplicado del mismo email.
- Stripe solo se integra cuando la lógica de negocio está establecida.

El proyecto debe quedar listo para integrarse con Stripe sin reescribir la lógica de negocio, ni dejar huecos en validaciones, logística de venta o entrega digital.

0) DECISION FINAL DE ARQUITECTURA
------------------------------------------------------------

0.1. Estructura funcional aceptada
- Frontend: catálogo, carrito, checkout, confirmación visual
- Backend: validación, ordenes, precios reales, documentos, emails
- Admin: beats, licencias, precios, PDFs, ventas
- Stripe: solamente como capa de pago final

0.2. Regla del negocio
- No se vende un beat sin licencia.
- No se acepta una licencia que no pertenezca al beat.
- No se calcula precio por beat sin tener en cuenta la licencia elegida.
- No se confirma una compra sin generar docs y correos.

0.3. Entregables obligatorios por compra
- ticket PDF
- licencia PDF específica para la licencia elegida
- email al cliente con documentos
- email duplicado al negocio
- registro de la compra

1) FILOSOFIA DE NEGOCIO Y ARQUITECTURA
------------------------------------------------------------

1.1. Principio central
- La compra debe ser el eje del sistema.
- El login/registro puede existir como soporte, pero no debe ser la base para vender.
- La tienda debe funcionar por compra directa con carrito, checkout y confirmación.
- El admin debe controlar catálogo, licencias, enlaces, precios, disponibilidad y ventas.

1.2. Misión del negocio
- Vender beats de forma profesional.
- Cada beat puede tener varias licencias y distintos precios.
- Cada compra debe generar un comprobante y un documento legal de licencia.
- Cada compra debe enviar un email automático tanto al cliente como al owner del negocio.
- El cliente debe recibir un ticket y la licencia apropiada según la licencia elegida.

1.3. Modelo recomendado de negocio
- Producto principal: beat
- Licencias: Basic, Premium, Exclusive, Broadcast, etc.
- Cada licencia tiene:
  - nombre
  - precio
  - descripción
  - permisos de uso
  - exclusividad
  - limite de streams
  - uso comercial / no comercial
  - archivo adjunto PDF de licencia

1.4. Diferencia clave entre beat y licencia
- El beat es el producto base.
- La licencia es la forma de uso comercial o de distribución del beat.
- La licencia debe estar embebida en la compra final.
- El precio no se calcula solo por beat, sino por beat + licencia elegida.

2) MODELO DE LICENCIAS Y PRECIOS POR BEAT
------------------------------------------------------------

2.1. Cada beat puede tener varias opciones de licencia
Ejemplo base:
- Basic License - $49
- Pro License - $149
- Premium License - $299
- Exclusive License - $1,500

2.2. Cada licencia debe tener datos claros
- id
- beatId
- name
- slug
- price
- description
- usageRights
- commercialUse
- isActive
- fileNamePdf

2.3. Regla importante
- El precio final debe calcularse con la licencia elegida, no con un precio fijo por beat.
- Si el beat tiene varios planes, el backend debe validar que la licencia exista y esté activa.
- Si la licencia no existe o no corresponde al beat, la compra debe rechazarse.

2.4. Data model recomendado
- beats
- licenses
- orders
- order_items
- payments
- customers
- email_logs

2.5. Validación obligatoria
- [ ] el beat existe
- [ ] la licencia pertenece al beat
- [ ] la licencia está activa
- [ ] el precio enviado coincide con el precio real de BD
- [ ] la compra no puede elegir una licencia inexistente

3) FLUJO DE COMPRA Y ORDENES
------------------------------------------------------------

3.1. Flujo principal correcto
1. Cliente entra a catálogo
2. Elige beat
3. Elige licencia del beat
4. Agrega al carrito
5. Revisa checkout
6. Completa nombre y email
7. El backend crea la orden
8. El backend valida el beat + licencia + precio
9. Se marca la orden en estado pending
10. Se confirma el pago o pago simulado
11. Se genera la licencia y el ticket
12. Se envía email al cliente
13. Se envía email duplicado al negocio
14. Se limpia carrito y se finaliza la compra

3.2. Reglas obligatorias del checkout
- [ ] no permitir carrito vacío
- [ ] no permitir beat inexistente
- [ ] no permitir licencia inválida
- [ ] no permitir precio incorrecto
- [ ] no permitir cantidades menores a 1
- [ ] no permitir duplicación por doble click o reintento
- [ ] el total debe calcularse en backend, nunca confiar en frontend
- [ ] la orden debe quedar en pending antes del pago

3.3. Estados recomendados
- pending: creada, esperando pago
- processing: pago en curso
- completed: pago confirmado
- cancelled: cancelada
- refunded: reembolsada

3.4. Estados de pago recomendados
- pending
- paid
- failed
- refunded

4.4. Detalles de orden

6) EMAIL AUTOMATICO AL FINALIZAR LA COMPRA
------------------------------------------------------------

6.1. Requerimiento central del negocio
Cuando una compra termine correctamente, el sistema debe enviar automáticamente:
- un email al cliente
- un email duplicado al correo del negocio

6.2. Email del cliente
Debe incluir:
- nombre del cliente
- nombre del beat
- nombre de la licencia comprada
- precio pagado
- fecha de compra
- numero de orden
- download links o instrucciones de acceso
- archivo PDF de licencia
- ticket de compra
- mensaje de agradecimiento

6.3. Email del negocio
Debe incluir:
- nombre del cliente
- email del cliente
- beat comprado
- licencia comprada
- precio final
- número de orden
- fecha de compra
- estado de pago
- copia del ticket
- copia de la licencia digital

6.4. Duplicado de compras
- [ ] cada compra debe generar una copia para el negocio
- [ ] el email del negocio no debe ser opcional
- [ ] toda compra debe quedar logueada con el estado del envío
- [ ] si falla el email al cliente, debe quedar registro del fallo y reintento manual

6.5. Recomendado para la entrega digital
- El email debe adjuntar el PDF de licencia
- El email debe incluir el ticket PDF o un enlace al ticket generado
- El PDF debe ser específico por licencia y por compra
- La licencia debe ser distinta según la licencia elegida

6.6. Archivos generados por la compra
- [ ] invoice.pdf o ticket.pdf
- [ ] license.pdf
- [ ] metadata con orderId, beatId, licenseId, customerEmail

6.7. Lógica ideal
- al confirmar compra, backend genera:
  - ticket PDF
  - licencia PDF según la licencia
  - payload de email con ambos documentos
- backend envía correo al cliente
- backend envía correo duplicado al negocio
- se marca en BD: emailEnviadoCliente = true / false
- se marca en BD: emailEnviadoAdmin = true / false

9) STRIPE PREPARACION
------------------------------------------------------------

9.1. Variables de entorno para Stripe
- [ ] STRIPE_SECRET_KEY

- [ ] STRIPE_WEBHOOK_SECRET

9.2. Patrón correcto para Stripe
- frontend crea la orden localmente
- backend valida la compra y la licencia
- backend crea la sesión de Stripe o PaymentIntent
- frontend redirige a Stripe
- Stripe devuelve al cliente a la app
- webhook confirma el pago
- backend marca la orden como completed y dispara emails PDF

9.3. Webhook recomendado
- [ ] checkout.session.completed
- [ ] payment_intent.succeeded

9.4. Reglas de integración con invoice/licencia
- [ ] el webhook no debe entregar documentos si la orden no es válida
- [ ] el webhook debe completar la orden antes de enviar email
- [ ] los PDFs deben generarse solo cuando el pago está confirmado

16) MISION DEL SIGUIENTE PASO
------------------------------------------------------------

La misión inmediata no es “integrar Stripe primero”, sino dejar bien resuelto el core del negocio: beat + licencia + precio + orden + validación + emails + documentos. Cuando ese núcleo esté sólido, Stripe es solo la capa de pago encima de un sistema que ya sabe vender y entregar correctamente.
